# Translating Texts (i18n)

Atscript ships no translation runtime. Your `.as` files are written in one source language, and every text in them is a **message id**: a translator (your map, i18next, FormatJS, …) looks the text up and returns the translation.

```atscript
export interface Signup {
  @meta.label 'Email'
  @expect.pattern '^\S+@\S+$', '', 'Enter a valid email'
  email: string

  @meta.label 'Password'
  @expect.minLength 8
  password: string
}
```

Here `'Email'`, `'Password'` and `'Enter a valid email'` are message ids. The `@expect.minLength` error has no text of its own: its id is the code `MIN_LENGTH`.

## The two kinds of ids

| The text comes from                                                                                         | Its id                                     | Example                                 |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------- |
| An annotation (`@meta.label`, `@meta.description`, a constraint's message argument, `@expect.message`, …) | the text itself, as written                | `'Enter a valid email'`                 |
| The validator's built-in message                                                                            | the error `code` (template with `{params}`) | `MIN_LENGTH` → `Mindestens {min} Zeichen` |

Error codes, their English templates and `localizeErrors()` are covered in [Validation Reference — Error Codes](/packages/typescript/validation-reference#error-codes).

Which annotations hold text is declared by their specs (`userText`). Core flags `@meta.label`, `@meta.description`, `@meta.required` and the message of every `@expect.*` constraint; plugins flag their own, see [User-facing Text](/plugin-development/annotation-system#user-facing-text-usertext).

## Serving a translated type

A server that sends types to a client ([Serialization](/packages/typescript/serialization)) translates them per request with `translateServed()`:

```typescript
import {
  serializeAnnotatedType,
  translateServed,
  VALIDATOR_MESSAGES,
} from '@atscript/typescript/utils'

import { Signup } from './signup.as'

const json = serializeAnnotatedType(Signup) // once, at startup

// t: your translator for the request's locale, returning undefined when it has no translation
function servedSignup(t: (text: string) => string | undefined) {
  const { value, texts } = translateServed(json, t)
  const templates: Record<string, string> = {}
  for (const code of Object.keys(VALIDATOR_MESSAGES)) {
    const template = t(code) // e.g. 'Mindestens {min} Zeichen'
    if (template !== undefined) templates[code] = template
  }
  return { ...value, $i18n: { ...templates, ...texts } }
}
```

- `t(text)` returns the translation, or `undefined` to keep the text.
- Every annotation holding text is translated, at any depth: props, array items, repeated types, reference targets, every item of a `multiple` annotation, the message field of a constraint. The exception is a primitive's built-in format message (`string.email`'s pattern message, …): it stays in English, because the validator reports it by its code (`EMAIL`), which the client translates through `$i18n`.
- The input is never changed, and is returned itself when nothing was translated — cache the result per type and locale.
- `translateServed()` accepts any JSON that carries serialized types, such as an envelope with the type inside it.

### `$i18n`: texts the client needs

Put the texts the client translates itself into the served type's `$i18n` field (a flat `{ [id]: text }` map, the templates first and `texts` over them):

- **Validator templates by code**, translated, keeping their `{name}` placeholders (`MIN_LENGTH: 'Mindestens {min} Zeichen'`).
- **`texts`** returned by `translateServed()`: the translated string literals of expressions (see below).

`deserializeAnnotatedType()` ignores `$i18n`.

::: tip Using moost?
`setTranslator()` from `moost` picks each request's locale and gives your code one translator, `useTranslate()`. See the [moost i18n guide](https://moost.org/moost/i18n).
:::

## Translating on the client

The served type's labels and messages are already translated. Validation errors the client produces use the built-in templates, so translate them with `$i18n`:

```typescript
import {
  deserializeAnnotatedType,
  localizeErrors,
  messagesTranslator,
} from '@atscript/typescript/utils'

const served = await fetch('/signup/meta').then(r => r.json())
const type = deserializeAnnotatedType(served)
const validator = type.validator()

if (!validator.validate(data, true)) {
  const errors = localizeErrors(validator.errors, messagesTranslator(served.$i18n ?? {}))
}
```

### Types compiled into the client

A type imported from a generated module (not served) still holds its texts in the source language. `translateUserText()` (since 0.2.10) translates one metadata key's value with the same rules and keys `translateServed()` uses, so one catalogue serves both sides:

```typescript
import { translateUserText } from '@atscript/typescript/utils'

const t = (text: string) => dict[text] // undefined keeps the text
const prop = Signup.type.props.get('email')!

const label = translateUserText('meta.label', prop.metadata.get('meta.label'), t)
const required = translateUserText('meta.required', prop.metadata.get('meta.required'), t)
// → { message: 'E-Mail nötig' }
```

It reads the text fields the annotation declares (`message` of `@meta.required`, each item of a `multiple` list, an option's `label`), leaves a primitive's built-in format message (reported by its code, see `$i18n`), and returns the value itself when nothing changes. It never changes its input. Keys that hold no text, and expressions, come back as they are: translate what an expression returns with `t`, by exact match.

## Expressions: texts computed on the client

Some annotations hold the source of a function the client runs, such as a computed label or a custom validator returning its message. A server cannot translate the result, which depends on the data. Their specs flag them `userText: 'expression'` instead:

```atscript
@ui.form.validate '(v) => v.password === v.confirm || "Passwords must match"'
```

`translateServed()` leaves the source as written, translates each string literal in it (`'…'`, `"…"`, and templates without `${…}`), and returns the translations in `texts`, keyed by the literal. The client looks a computed result up in `$i18n` by exact match: `"Passwords must match"` is translated, while a result built by concatenation (`"Hello " + name`) is not.

## DOs and DON'Ts

- **DO write each text once, in the source language,** and use it as the id in your translations.
- **DO serve validator templates by code in `$i18n`** so client-side validation speaks the user's language.
- **DON'T branch on `message`** in clients: it changes with the locale. Use `code` and `params`.
- **DON'T build texts from pieces** in expressions (`'Add ' + label`); exact-match translation only finds whole literals.
- **DON'T expect derived texts to be translated:** a label that is not written in an annotation (taken from the field name, say) has no id.
