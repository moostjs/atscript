# Upgrading to 0.2

Atscript 0.2.0 changes the generated runtime code and tightens a few compile rules. Most projects only need step 1. Each item links to the page that documents the current behaviour.

## 1. Regenerate every generated module

Modules generated by atscript 0.1.110 or earlier do not load on the 0.2 runtime: they call builder methods it no longer has (`refTo`, `cloneRefProp`). Rebuild your own `.as` output and every package you depend on that ships generated `.as` code. There is no compatibility mode. See [Packages Built with an Earlier Version](/packages/typescript/build-setup#packages-built-with-an-earlier-version).

Code that builds types by hand uses `defineAnnotatedType().ref(Target)` (or `.ref(Target, ['field'])` for a field) instead of `refTo`.

## 2. Fix the new compile errors

0.1.x still generated JavaScript for a file that had error diagnostics. 0.2 refuses: any error in a file, including a plugin annotation error such as an argument outside its allowed values, fails code generation for that file. Fix every error your editor or build reports.

Schemas that compiled on 0.1.x can fail on 0.2 in these cases:

| Error                                                      | What to do                                                                                                                                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Unknown member "…"` on a type path through a union        | A typo that 0.1.x accepted silently (`M.work.hh` with `type M = Job \| null`). Fix the path. See [Type Paths](/packages/typescript/interfaces-types#reference-a-field-type-paths) |
| `"…" names phantom and non-phantom fields through a union` | A type path reaches a `phantom` field on one branch and a data field on another. Make the branches agree, or point at one branch                                                  |
| `An interface can't extend a union; use a merge`           | Write `type Post = Content & { … }` instead of `interface Post extends Content`. See [Interface Extends](/packages/typescript/interfaces-types#interface-extends)                 |
| `Circular chain reference "…": it resolves to itself`      | A merged or inherited field typed by a path back to itself; 0.1.x overflowed the stack. Give the field its real type                                                              |
| `A block's path can't cross the type path it splits.`      | Put the `annotate` block on the union instead of one branch. See [Type Paths](/packages/typescript/interfaces-types#reference-a-field-type-paths)                                 |

A production build now also loads every generated module once and fails when one throws. That failure is a code generation bug to report, not a schema error. See [Import cycles need native ES modules](/packages/typescript/build-setup#import-cycles-need-native-es-modules) for where the check runs and the `loadCheck` option.

## 3. Check behaviour changes

- **A `.ts` config that fails while it is evaluated stops the build** (0.2.19, a fix). The common case is a config that imports a package that is not installed or not built yet (a workspace plugin before its first build); a config that throws does the same. Before, `asc` and the bundler plugin logged `Could not load config file …` and went on with an empty config — without your plugins, so their annotations were reported as unknown; a `.js` config already failed. Now `asc` exits with an error and the bundler plugin fails the build, the dev server and the test run. The VSCode extension logs the error once and checks your files with the built-in config until the config file changes or the editor restarts.
- **The bundler plugin loads `atscript.config.*` when a build starts** (0.2.19): at the start of every build and watch rebuild, when the dev server starts, and when a test run (Vitest) starts — before, at the first `.as` module the bundler loaded. So a project that uses the plugin without importing any `.as` file now loads its config on every start, and a config that fails to load (above) stops the build, the dev server or the test run from starting even when no `.as` file is imported. See [Build Setup](/packages/typescript/build-setup).
- **The warning for an `annotate` block on another package's type has its own text for that package's files** (0.2.16, wording only). When the annotated type and the files using it belong to another package — a dependency, or a linked workspace package — the warning names those files `<package name>/<path in the package>` instead of a relative path through `node_modules`, and says that they cannot import the block: their package's own build never includes it, and at runtime it reaches them only if its module is loaded before they first use the type. To change the type only for your own code, annotate a type of your own (`interface X extends T`, or `annotate T as X`). That warning no longer contains `without importing this file`; a build-log filter matching that text no longer catches it. Files of another package that use a type your own package declares keep the old warning, which tells you to import the block's file from the type's file; they are named by package too. The warning for your own files keeps its text, but no longer suggests importing the block from the declaring file when that file belongs to another package. See [When blocks apply](/packages/typescript/ad-hoc-annotations#when-blocks-apply).
- **Errors inside a nullable object or array are reported at their own paths** (0.2.14, an error-code change in a patch release). A field typed `T | null` holding an object (or an array) like `T` that fails `T` reports `T`'s errors (`address.zip` with code `TYPE`, a plugin's own error) instead of one `UNION` error at the field with those errors in `details`. Code that matched `code === 'UNION'` on such a field should read the specific errors. A value of another kind (`5`, or `[]` for an object `T`) still reports `UNION`. The field's `@expect.message` no longer replaces the errors inside `T`; it still covers a value of another kind. See [Nullable objects and arrays](/packages/typescript/validation-reference#nullable-objects-and-arrays).
- **A missing `@meta.required` field reports `REQUIRED`** (0.2.10, an error-code change in a patch release). A non-optional `@meta.required` field that is missing, or `null` where its type does not accept `null`, fails with code `REQUIRED` (`REQUIRED_CHECKED` for booleans) and the annotation's message instead of `TYPE` (or `UNION`). Update catalogs and code that matched `TYPE` for these fields. See [Built-in Validation Rules](/packages/typescript/validation-reference#built-in-validation-rules).
- **`unknownProps: 'strip'` deletes keys only when validation passes.** A failed validation, a rejected union branch, or a plugin's `ctx.validateAnnotatedType(...)` call that returns `false` strips nothing. See [`unknownProps`](/packages/typescript/validation-reference#unknownprops).
- **Raw writes to a type tree need `invalidateCompiledValidators()`** for the interpreted validator and every metadata reader too, not only compiled checks: swapping a node's map (`node.metadata = X`) or editing a stored value in place. Writes through `set` / `delete` / `annotate()` are tracked as before. See [Runtime Metadata](/plugin-development/runtime-metadata#writing-at-runtime).
- **`.d.ts` type paths** are written as `TAtscriptField<T, "k">` steps (a type-only export of `@atscript/typescript/utils`) instead of `T["k"]`, so a path through a union or an optional property type-checks. See [Type paths](/packages/typescript/code-generation#type-paths).
- **A bare alias is the same object at runtime.** `export type X = Y` is `Y` itself; an alias with annotations of its own, or an `annotate Y as X` copy, is a separate node that reads through `Y`. See [The Annotated Type](/packages/typescript/type-definitions#the-annotated-type).
- **An intersection of object types is one object type at runtime** (the compiler writes the merge). See [How a merge is built](/packages/typescript/interfaces-types#how-a-merge-is-built).

## 4. Plugin authors

- **New hook `buildStart(config)`** (0.2.19). It runs after every plugin's `config()` and before any `.as` file is discovered or read, in `asc` / `build()` and in every build of the bundler plugin (not in the editor): write `.as` files generated from another source there instead of in your plugin's factory. It must be idempotent and write a file only when its content changes. See [buildStart()](/plugin-development/plugin-hooks#buildstart).
- **`config.rootDir` is absolute in every hook** (0.2.19). The bundler plugin passed the value as written in the config (`'src'`, or nothing), and so did the editor when the config set one; the `asc` CLI already passed it absolute. Resolve paths against it directly.
- **`config()` runs before the first document is resolved or loaded, and once per loaded config** (0.2.19, a fix). With `asc` and the bundler, the first document's `resolve()` and `load()` ran before it; the editor ran it again for every document. A plugin that reads in `resolve()` / `load()` what its `config()` saw now sees it from the first document on.
- `doc.unwindType()` / `doc.unwindRef()` on a type path through a union return the field, or `fields` when the path names several. See [`doc.unwindType`](/plugin-development/architecture#doc-unwindtype-name-chain).
- `resolveFieldRefAt()` and `resolveQueryFieldRef()` return `undefined` when a path names several fields; `resolveFieldRefsAt()` returns all of them.
- `render(doc, format, options)` receives the render options; a plugin wrapping another plugin's `render` must pass them on. See [render()](/plugin-development/plugin-hooks#render).
- **A field's `ownerNode` is the structure that declares it, whatever else refers to its interface** (0.2.18, a fix). From an annotation token, `token.parentNode.ownerNode.ownerNode` reaches the interface the field is written in. Before, an interface with `extends` that another interface extended, or whose field a type path named (`Table.field`), handed its own fields to the merged structure, and an annotate-alias copy did the same to the fields of its source, so the walk ended without an interface. A plugin rule such as "valid only on a field of an annotated interface" then refused a correct schema, depending on what else the file declared.

Upgrading from an older 0.1.x release as well? The validation tightenings of 0.1.100–0.1.104 (non-finite numbers, zero bounds, nullable constraints, `string.required`) are listed with upgrade notes in the [Validation Reference](/packages/typescript/validation-reference#built-in-validation-rules).
